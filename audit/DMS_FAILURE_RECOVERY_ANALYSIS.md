## Reliability implications

1. **Progress may not equal delivered count.** PHP persists process progress before native internal completion semantics are known; child stdout is redirected away.
2. **Force-kill creates an ambiguous boundary.** kill -9 can interrupt a recipient batch or message transaction; the visible caller clears state without proving whether the last unit was accepted.
3. **Snapshot drift is possible.** Suppression and audience materialization precede send; later data/suppression changes may not affect that file.
4. **Filesystem and database state are coupled.** Campaign rows, snapshot/config files, history and process launch are separate operations; atomic recovery was not established.
5. **Event and PMTA replay may not be idempotent.** Visitor rows lack a unique event key; PMTA processing increments counters while moving files.
6. **Retry configuration may trade delivery for loss.** Horizon's configured tries=1 is low, but actual active configuration and job overrides were not fully enumerated.
7. **Batch concurrency is partly opaque.** Gmail parallel mode explicitly allows 100 concurrent forks. The native managed code has reachable `Parallel.ForEach` calls and LINQ `Skip`/`Take`, but recipient association, chunk size, worker cap, rate limits, and backpressure are unknown.
8. **Native result aggregation may race.** The `send` worker pool starts one `Task.Run` per array item, while each worker adds to the same instance `List<string>` on normal and exception paths. The collection has no visible synchronization in the worker CIL. `List<T>` instance members are not guaranteed thread-safe ([Microsoft documentation](https://learn.microsoft.com/en-us/dotnet/api/system.collections.generic.list-1#thread-safety)); concurrent corruption or missing entries are a static risk, not an observed runtime incident. The contents are obfuscated and do not yet establish delivery outcomes.
9. **Handled worker errors may not fail the parent task.** A fresh static CIL check shows the worker's outer `System.Exception` handler logs the message, appends an obfuscated result string, and returns without rethrowing. An exception handled there does not itself fault the worker `Task` or propagate through `Task.WaitAll`. The resulting strings are written to child stdout, which the inspected PHP launcher redirects to `/dev/null`; whether a separate database or PMTA-feedback path reconciles that item remains unknown.
