## How the string blocker was resolved

A supplementary offline CIL/resource analysis reconstructed the binary's static string resolver (`0x0600048D` calling `0x0600048E`): ID-to-resource offset, redirect records, record flags and length, assembly public-key-token rotation, the LCG/key-byte transform, and the one compressed record. The code **read** the copied assembly and resource; it did not load or invoke .NET target code. All 936 distinct literal IDs passed to this resolver from method bodies yielded decoded payloads. Some payloads are control/binary strings, so this count does not imply that every value is a human-readable feature label. The private decoded manifest was intentionally not copied into the audit because arbitrary embedded strings can contain sensitive data. Its semantics were cross-checked against PHP source keys and commands (`campaign:details`, `main_ip`, `main_port`), SQL/migrations, and SMTP verbs. A Base64-shaped key record validated without disclosure. This reconstruction is analyst inference backed by the exact REA CIL identity; decoded strings are not runtime observations.

## Resolved execution contract

1. PHP builds a Base64 JSON config for a standard campaign with `campaignId`, `sendId`, `userId`, pacing, the `artisan` path, and related parameters; it does **not** put servers or content in that initial config. See the fresh source snapshot `app/Actions/CampaignAction.php:292-326`.
2. Managed `Main` reads `args[0]` as mode and `args[1]` as the file, then Base64-decodes/parses JSON. Literal mode names are now decoded, including all eight `send_` modes (`delay`, `delayp`, `delayps`, `hs`, `hsp`, `hsps`, `pickup`, `pickups`), corresponding `drop_`, `drop_test_`, `warmup_` and `warmup_test_` variants, and `global_test`. The formerly ambiguous 11-character `g`/JArray/TCP branch is **`global_test`**; the 12-character `s`/JArray/TCP branch is **`send_delayps`**; the 10-character `d`/Dapper branch is **`drop_delay`**. These labels are literal operands in `Main` (`0x060005FA`), not shape guesses.
3. In the campaign path, native code starts `/usr/bin/php` and uses `campaign:details ` with the configured artisan path and campaign ID (`0x06000435`, `0x06000261`). `CampaignDetails.php:17-58` checks restriction/activity and outputs JSON containing the return path, test addresses, header, body, from/subject assets, creative, negative ID, server groups, placeholders, and recipient file. The sender then parses these named fields, including `servers`, `main_ip`, `main_port`, `ips`, and `vmta` (`0x060004D1` and sibling mode handlers).
4. PHP `build_send_ips()` takes the persisted `Server::ip` for `main_ip` and `config('settings.pmta_port')` for `main_port` (`app/Utilities/helpers.php:933-977`). PMTA installation source configures its listener using that same setting. Together with native TCP connect using these fields, this establishes the **intended configured PMTA listener endpoint** for ordinary campaign mode. Actual production settings, socket traffic, and listener identity were not read, so this is a source/artifact contract, not a captured connection.
5. The inspected `send_delay` path writes `MAIL FROM: <...>`, `RCPT TO: <...>`, then `DATA` (`0x06000559`). It writes `x-envid:`, `x-job:`, `x-virtual-mta:`, generated message content, and a terminating dot (`0x0600055A`). It sends `QUIT` and reconnects every 500 messages (`0x0600055B`, `0x06000557`). Another transport branch has `EHLO`, optional `AUTH CRAM-MD5`, `XACK OFF`, `XMRG FROM:<`, `XDFN`, and `XPRT 1 LAST` (`0x06000029`, `0x06000178`, `0x0600017E`, `0x0600017F`). Thus SMTP command construction is established statically. Different mode branches can use different helpers; do not ascribe every verb to every mode.
6. The sender writes SQL for `campaigns`, `drops`, and `seed_campaigns` progress and status through Dapper. Exact strings include `update campaigns set send_progress = @newProgress where id = @id` (`0x06000264`) and `update campaigns set send_status = @newStatus, send_pid = null where id = @id` (`0x06000265`), with equivalent drop/seed updates. It reads campaign `send_progress`, `send_count`, and `is_restricted` and checks a termination condition (`0x060004D1`). This corrects the previous statement that durable sender status writes were unestablished.
7. Progress is **not proof of acceptance or delivery**. In the inspected `send_delay` chain, `0x06000558` writes a line to the stream; `0x06000559` and `0x0600055A` do not consume a per-recipient SMTP reply before progress updates. The connection object creates a reader, but these selected helpers do not use it to confirm individual recipients. A different branch does parse replies. The exact status transition deserves caution: `send_delay` has a `finish` write at an already-complete entry condition, while several paths write `start` and clear PID, including a total-send end path. A terminal success state must not be inferred from a status label alone.

## Consequences for the AlphaLink handoff

AlphaLink can now model the *reference behavior* as: audience snapshot and suppression in Laravel; launch config file; native worker fetches campaign details; server groups resolve to a configured PMTA listener; SMTP submission; sender progress/status writes; later PMTA delivery/bounce import; separate tracking and affiliate conversion streams. The existing [complete DMS conclusion](DMS_COMPLETE_CONCLUSION_2026-10-22.md) covers frontend modules, data model, campaign/drop/warmup/Gmail flows, PMTA management, tracking, reporting, integrations and security boundaries. This sender correction closes its largest static reverse-engineering gap.

The reference does **not** prove accepted delivery for each recipient, robust retry or checkpoint behavior, exact final MIME bytes, observed TLS settings, live PMTA configuration, PHPMailer participation, complaint processing, production event accuracy, or current account data. Those remain design questions for AlphaLink, not features to copy blindly. No AlphaLink code or stack was chosen during this read-only inspection.
