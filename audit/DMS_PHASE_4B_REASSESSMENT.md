## Direct answers to the owner’s questions

### What language and technology is DMS built with?

The application source is Laravel 10.38.2 / PHP 8.1, configured for PostgreSQL and Redis/Horizon. The campaign engine is a separate .NET 7 single-file Linux x64 sender. This identifies the inspected build and declared configuration, not every live deployment component. New static CIL evidence ties a TCP host/port writer and a reply parser to the same JArray worker object; SMTP compatibility is the leading protocol inference. Obfuscated command text, reply-stage meaning, PowerMTA identity, and durable outcomes remain unverified. The sender is still not sufficiently understood to reproduce its message construction, recipient mapping, retry policy, or success accounting.

### How does it track opens, clicks, leads and unsubscribes?

- The installed mini-app serves campaign/drop open pixels, click redirects, bot endpoints and unsubscribe links.
- Its link token is Base64-encoded fields plus an Adler-32 checksum; the fields identify campaign/send/recipient/list/ISP/server/IP/domain/from/subject/creative and a random attribution token. Base64 is encoding, not confidentiality, and Adler-32 is not a cryptographic MAC.
- The mini-app sends token component 13 (the checksum) when asking the main API for campaign/drop metadata; its stats payload sends component 12 (the random attribution token). These are separate values with separate purposes.
- Click and offer-unsubscribe requests ask the main app for the current offer destination, then send a statistics event. The main app validates a shared mini-app key and queues visitor jobs. Open and bot routes also send events; the open route returns a static PNG.
- Campaign click-through adds provider attribution values for HitPath, Cake, HasOffers or EverFlow. Affiliate conversion reports are polled separately and matched through provider fields such as s2; lead rows and recipient state are updated by SponsorLead.
- PMTA delivery and bounce CSV files feed a separate scheduled ingestion path and counters. A manual reply extractor reads inbound mbox files but does not show complaint-specific state changes.
- The campaign unsubscribe route records an offer unsubscribe and redirects to that offer’s unsubscribe URL. The public /unsubscribe form without its u flag submits a separate global opt_out. These scopes are not interchangeable.

### What API integrations exist?

Source-supported adapters include five affiliate networks; GoDaddy and Namecheap DNS/registrar APIs; eight cloud provisioning providers; Google Gmail send/draft APIs; Google Workspace Directory account synchronization; Microsoft OAuth and Outlook account push into PMTA configuration; Firebase Auth; Bitly and several short-link services; Imgur; Telegram; ip-api Pro with MaxMind fallback; disposable-email and SpamAssassin checks; SPF/DNS utilities; and suppression-file acquisition from partner, Dropbox and Google-sheet sources. The app also has its own mini-app event API and PMTA/server management interfaces.

This is a list of implemented source paths, not a list of live connected accounts. No external service was contacted. In particular, Outlook OAuth/token handling is visible, but a direct Graph sendMail call was not established; Gmail has a separate verified send path.

### How does it install PMTA with root credentials?

The admin flow records a server address, SSH port, username, password or private key, and login type. The schema defaults the username to root and stores the credential in a mediumText column; the model has no application-level encryption cast for that field. ServersInstallFactory uses phpseclib SFTP to log in and select a CentOS 7 or CentOS 9-derived installer. The install command configures the host, removes old packages, changes services, optionally installs the tracking mini-app, configures DNS records for owned domains, installs PMTA, creates VMTA/domain/IP/ISP configuration, and may install IMAP, proxy, HTTPS and firewall settings.

The PMTA installer removes prior PMTA directories and data, uninstalls the package, and kills processes listening on TCP port 25 before installing the selected local RPM/patched package and configuration. The setup code also disables SELinux and can stop/disable host firewalls depending on its firewall setting. This is a high-impact, state-changing sequence with no visible transaction or rollback. It is source behavior only: no server-install command was run and no live server was inspected.

### How are lists, recipients and ISPs managed?

An ISP is a DMS grouping/access and sender-configuration object, not an identified external ISP API. Its fields include allowed users/sponsors, tracked countries and quality_emails; those quality emails are passed into campaign/drop sender configuration, but their precise sender-engine effect is unknown. Lists belong to one ISP, carry country, access controls, six recipient-type locks and an is_tracked flag. ISP access changes are propagated to its lists in application loops.

The recipient states include fresh, delivery, open, click, lead, unsubscribe, opt_out, proxy, bot, blacklist and hard_bounce. The ACTIVE_TYPES list includes only fresh through unsubscribe; opt_out, proxy, bot, blacklist and hard_bounce are excluded. The inspected recipient table has a globally unique email address and one lists_id foreign key, so one address belongs to one list in this schema. Upload processing lowercases and validates addresses and stages/imports them with PostgreSQL ON CONFLICT DO NOTHING. Re-uploading an existing address into another list therefore does not create another membership or visibly move it. The parser splits lines on commas rather than using a full CSV reader; quoted fields can be mishandled. The optional import filter’s argument order appears inconsistent with its comment and should be reviewed before reuse.

### How do affiliate offers sync?

Offer import is an explicit user action: an admin selects a sponsor and offer IDs, the corresponding adapter fetches those IDs, and DMS adds offers that do not already exist (including soft-deleted records in the duplicate check). Manual offer creation is also supported. Daily refresh updates known active/live offers’ name, status, payout, destination, unsubscribe URL and creatives; a separate scheduled task refreshes stale/missing suppression files. These jobs do **not** discover new offer IDs automatically. A five-minute scheduled process imports affiliate conversion reports, with a separate month-to-date reconciliation job.

## Critical findings

### Recipient policy and suppression

1. **No explicit consent evidence model was found in the inspected subscriber schema.** Recipient type and offer exclusions are operational state, not proof of consent, purpose, source, timestamp, or collection notice. Phase 4A correctly treats this as a first-order product requirement.
2. **Unsubscribe scope needs a deliberate AlphaLink rule.** DMS has offer-scoped unsubscribe and a distinct global opt-out. Complaints and hard bounces need explicit precedence and durable suppression semantics. Do not infer a compliant global policy from the DMS state names.
3. **A likely reporting mismatch exists.** Global opt-out changes recipient type to opt_out and writes an email log. Campaign and drop aggregators count visitor type optout (without the underscore), and the inspected global opt-out path does not create a visitor. This suggests the displayed campaign/drop opt-out aggregate may not receive ordinary global opt-outs; live metric impact was not checked.
4. **Virtual-list suppression can preserve an unsubscribed record.** The reply extractor includes `unsubscribe` recipient rows in a `reply-<name>` mix. Campaign creation passes selected lists through `Suppression`, whose virtual-list branch reads stored mix rows without refreshing current lifecycle state or `excluded_offers`; that row can enter the campaign snapshot unless the separate offer suppression file removes it. Whether the native sender filters it later is unknown. More generally, suppression and list filtering happen before snapshot materialization, and the inspected path does not establish that later opt-outs, complaints or list changes invalidate existing send files.

### Tracking, attribution and feedback

1. The mini-app’s shared key and token checksum are static trust mechanisms. The checksum is not cryptographic, tokens are transparent encodings, and the inspected token helper shows no expiry. The key’s rotation, distribution and exposure controls are unknown.
2. Campaign/drop stats endpoints have no route-specific throttle, while the shared api limiter is commented out in source; only subscribe, opt-out and contact routes show explicit throttles. Edge/WAF protections and production limits are unknown.
3. Event jobs and visitor persistence do not show one universal idempotency key. Retries can plausibly duplicate visitor events while email-log token writes may collapse; actual production duplicate rates are unknown.
4. CentOS 9 PMTA configuration creates a feedback-loop processor address and appends inbound mail to /etc/pmta/inbound/{domain}. ReplyExtract downloads such mailbox files over SFTP and MboxParserJs extracts From, Message-ID and date for a virtual reply audience. The reviewed path has no visible ARF/complaint classifier, complaint-to-recipient match, or complaint suppression update. Live FBL routing and other external processing remain unknown.
5. IP geolocation uses ip-api Pro plus local MaxMind fallback for visitor-event jobs, landing forms, geo-targeted redirects, affiliate conversions and server country completion. The mini-app derives the transmitted address with Laravel `Request::ip()`, but effective trusted-proxy/ingress behavior is unknown. If both geolocation sources fail, geo-target rejection is skipped. The API key is sent in the GET query. Active settings, key validity, MaxMind files and log retention were not inspected; details and source anchors are in [EXTERNAL_INTEGRATIONS.md](EXTERNAL_INTEGRATIONS.md#ip-geolocation-ip-api-pro-with-maxmind-fallback).

### Data and affiliate operations

1. Global one-list membership is a significant product constraint. AlphaLink should decide whether it intentionally supports multi-list membership, one canonical contact with many audience memberships, or a different model. Do not reproduce ON CONFLICT DO NOTHING semantics silently.
2. Source import parsing and filtering need explicit data-quality behavior: RFC-style CSV handling, normalization, duplicate disposition, rejected-row reporting, provenance, and re-import safety.
3. Affiliate conversion deduplication is visible as an application lookup by revenue_id; a database uniqueness guarantee was not established in the reviewed path. Provider retries, concurrent imports, pagination/cursors, reversal/refund corrections and attribution windows need explicit contracts.
4. New offer discovery is manual even though known offers refresh automatically. The product must choose whether AlphaLink needs scheduled catalog discovery, selected-ID refresh, or only manual import; these are different workflows.

## Review of the Phase 4A specification

- **Evidence correction:** PHASE_4A_DECISIONS.md D-14 and the feature inventory state that PMTA file ingestion is mapped but no dedicated complaint/FBL path was found. Replace that statement in a later approved design revision with the more precise finding above: PMTA FBL config and inbound mbox/reply extraction exist; complaint classification and suppression are unverified. This assessment does not edit the Phase 4A documents.
- **Scope mismatch:** D-06 leaves the first release undecided while the requirements enumerate campaign, tracking, analytics, affiliates, multiple send paths, infrastructure control, cloud/registrar operations, and utility tools. This is a scope and sequencing gap. The design needs an explicit thin first release and deferred modules before estimates or architecture commitments.
- **Conditional infrastructure ownership:** D-08 asks whether AlphaLink should manage infrastructure, while the architecture gives infrastructure control a first-class module and detailed lifecycle contracts. Mark that module conditional until the owner decides; otherwise the design quietly assumes the answer.
- **Accessibility decision conflict:** The PRD treats WCAG 2.2 AA as a release-blocking acceptance target, while D-18 still asks the owner to confirm it. Either make it the approved baseline or mark it as a proposed target with a decision owner and date.
- **Data-model delta:** The AlphaLink tenancy and recipient model must explicitly improve on or intentionally preserve DMS’s single-list email constraint. Workspace scoping alone does not resolve contact identity, list membership, consent purpose, dedupe, or cross-workspace suppression.
- **Tracking-policy gap:** The current requirements should distinguish open/click/offer-unsubscribe/global-opt-out/complaint/bounce and define public event authentication, replay protection, privacy retention and bot classification. “Authenticated event request” is not sufficient as a requirement for anonymous pixel/click clients.
- **Complexity risk:** The proposed module boundaries, durable event envelopes, outbox-style delivery and broad recovery contracts are reasonable design tools, but applying all of them to every internal interaction before selecting the first-release use cases risks overbuilding. Keep the safety invariants and make durability/idempotency mandatory at real loss/duplicate boundaries; defer infrastructure-level complexity until measured workload and ownership justify it. The architecture does not require microservices, and this is a staging concern rather than a direct contradiction.
- **Unapproved targets:** PRD throughput, latency, availability, RPO/RTO and accessibility targets are hypotheses. Keep them as hypotheses until workload, cost, support coverage and benchmarks are approved.
