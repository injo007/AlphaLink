# AlphaLink UI Behavior Contract

## Product context

- **Audience:** Workspace owners, administrators, campaign operators, and privacy officers.
- **Primary jobs:** Sign in, choose an authorized workspace, review campaign revisions or audience-list state, and use server and PMTA controls within an active workspace.
- **Target market(s):** Not selected. English is the initial interface language; no legal or jurisdictional policy is implied.
- **Accessibility target:** WCAG 2.2 AA baseline for semantics, keyboard access, visible focus, status names, and contrast.
- **Business evidence:** `../../audit/ALPHALINK_ADVANCED_REFERENCE_SYSTEM_2026-10-22.md` defines the intended architecture and the current no-sending boundary. The live API route groups and `EnsureWorkspaceMember` / `EnsureWorkspaceRole` middleware define implemented access behavior.

## Visual contract

- **Design system:** `DESIGN.md`.
- **Token ownership:** `resources/css/app.css` owns runtime variables; `DESIGN.md` documents their accepted values.
- **Themes:** Light only.
- **Locale:** English only. Dates follow the configured application timezone.

## Campaign composer field behavior

- From and Subject offer assets are optional rotation lists. Saving or updating a campaign does not require choosing them; leave them empty when the Header contains literal values. The backend continues to validate any selected asset against the active offer.
- Campaign targeting requires selected Lists, Servers, and at least one IP for Save/Edit. The visible Available IPs and Selected IPs lists are backed by the hidden `send-ips` form control; double-click moves a selected entry in either direction. Arrow controls remain available for keyboard users.
- The authoritative implementation is `resources/views/console/campaigns/create.blade.php`; the actual selection and required-state behavior is exercised by `tests/js/campaign-create-controls.test.js` and the campaign catalog feature tests.

## Workflow and state

- `/sign-in` authenticates an existing account. A generic error appears inline; repeated failures are rate-limited. Success regenerates the session and returns the user to the intended destination.
- `/app` redirects a single-workspace member to that workspace, lists multiple active memberships, or explains when no active workspace is assigned.
- Every workspace route resolves the workspace through the signed-in user's active membership. A non-member sees not-found; a member without the capability sees forbidden.
- Campaigns → SEND opens the DMS-shaped operational register and draft/revision forms. Draft save persists targeting, suppression manifest, Return Path, Email Test addresses, selected domain, raw Header/Body and send options; content revisions preserve the exact prior recipient snapshot. The DMS saved-header control loads/saves/deletes raw header text. Campaign Negatives follows DMS’s per-user upload/list/download/delete flow; its selected ID is saved with a draft, but AlphaLink does not claim sender use or recipient filtering. Manual Campaign Test logs display the operator-entered Email Test recipients from that test snapshot; the snapshot is encrypted at rest and visible in the campaign owner’s log. Audience contact addresses are not exposed by campaign pages. Delivery actions remain unavailable until the source-equivalent sender, lifecycle, history, schedule and recovery behavior is verified. The workspace PMTA HTTP port is consumed by panel links and next install/reinstall inputs; saving it does not rewrite already-installed hosts.
- Offers expose a dedicated suppression-file page per offer, matching DMS’s separation between an offer’s saved file and Drops suppression runs/history. The Drops page remains the run/history surface and shows the selected offer’s saved-file state and link to its manager.
- Every active workspace member can open the server Console from its row. It accepts arbitrary commands under the saved SSH account after DMS-compatible architecture/distribution checks; output is displayed as text. AlphaLink verifies the internally saved host key without prompting for a fingerprint.
- Every active workspace member can register a server with a public IP, provider and password or SSH key. The credential is encrypted in a separate row and is never rendered or returned. Members can edit provider, name, address, port, username, login type and expiry; leaving the credential blank preserves the saved secret, while connection changes rotate it and invalidate preflight evidence. Test Connection can use the saved secret and never asks for a host fingerprint. Registration starts in `pending_preflight` and does not contact the server. Test Connection is a separate SSH/SFTP login and never asks the operator for a host fingerprint. Read-only preflight automatically records the first SSH host key and rejects a later key change without requesting fingerprint input.
- `/app/workspaces/{workspace}/infrastructure` redirects to the DMS-matched Servers list. The former combined Add server / TXT verification / installation-preview page is removed from the browser UI. Server, domain, provider, and installation-settings work belongs to their separately mapped pages.
- The Miscellaneous sidebar uses the DMS label **SETTINGS**. Its Settings page contains DMS-mapped General Settings and PMTA Domains Settings tabs in the same location as DMS; the PMTA Domains tab is selected on the same route. Install Settings redirects to this page. General values and PMTA domain text are workspace-scoped. PMTA HTTP port is consumed immediately by AlphaLink panel links and by the next install/reinstall inputs; the live workspace value is 2426. It does not rewrite an already-installed host. Credentials are encrypted, never prefilled into the form, preserved on blank edits, and removed from flashed validation input. Bitly/Imgur callback behavior and downstream consumers remain incomplete. Subscribers and Contacts have owner/admin, workspace-scoped, searchable DataTables and Contacts has a text-only SEE MORE dialog; their local tables remain empty until corresponding AlphaLink intake writers exist. Horizon has an owner/admin route that states the Horizon package/dashboard is unavailable, shows the configured queue connection, and offers no restart action; active worker state is not verified. App Health checks uptime, RAM, database, storage, and queue configuration, runs when no cached report exists, and is scheduled once per minute. It does not send external failure notifications or infer queue worker activity. App Errors is an owner/admin summary view over AlphaLink logs; it redacts exception JSON, stack paths, common secrets, emails, IPs, URLs, and database details, so it is not full `/log-viewer` parity.
