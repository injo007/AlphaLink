# Source-backed business rules in the active server slice

## DMS-SRV-001 — server registration

**Evidence:** E-SRV-01 is the read-only source snapshot at `resources/views/admin/servers/create.blade.php`, `app/Http/Controllers/Admin/ServerController.php:58-111`, and `app/Actions/ServerAction.php:23-65`. E-SRV-LIVE-01 is a fresh browser observation through the authenticated GET-only relay; it confirms the live form and its visible defaults but is not a live registration test.

The DMS form presents a provider dropdown, name (default `server`), an IP textarea, port (default 22), SSH username (default `root`), login type (`Password` or `Ssh Key`), credential, expiry (default approximately 30 days), **TEST CONNECTION**, and **SAVE**. The form's IP handling splits on newline, removes blank strings and exact duplicates; it does not trim each line. The controller requires a numeric provider ID, name string length 2–255, at least one IP, numeric port, username, login type in `password|ssh_key`, credential length at least four, and an expiry date no earlier than today. Exact provider-existence validation, invalid-line feedback and current provider catalogue state are not established here.

`ServerAction::add` processes each supplied IP. A valid IP matching a soft-deleted server is restored and its registration fields refreshed. Remaining new IPs are inserted in one bulk `insertOrIgnore`, so live duplicates are not replaced. There is no transaction covering the whole multi-IP operation: an earlier restore is not rolled back because a later new-row operation fails. Each new server is a separate server record for one IP. DMS Test Connection is a separate request: it validates connection fields and invokes the SSH/SFTP handler for each IP. The DMS form has no fingerprint field or confirmation step; source shows no explicit fingerprint input at the Test Connection or installer call site. Live connection outcomes were not exercised.

AlphaLink implements the same visible form order/defaults, newline split/blank removal/exact deduplication, provider dropdown order seen in the live page, per-IP cardinality, duplicate skip and restore path. It uses a local transaction for a new-record batch and protects credentials with application encryption, workspace-scoped access, idempotency, and an append-only audit record. Test Connection now logs in directly over SSH/SFTP without asking for a fingerprint. Installation preflight automatically pins the SSH host key on first use and rejects a later key change without requesting user input. That automatic pin is an internal transport safeguard, not a DMS business rule. The provider catalogue's authoritative current contents, DMS credential storage rules, exact multi-IP partial-failure response, and real Test Connection result equivalence remain unresolved. Private, reserved and special-use IP ranges that the PHP filter accepted are blocked before local socket creation using the IANA registry ranges in E-ADDR-01; this is an AlphaLink safety boundary.

Browser evidence confirms the DMS and AlphaLink Add forms and their Add modals were compared at the same 863×892 viewport. A local synthetic registration was saved, appeared in the workspace-scoped server list without returning the secret, and was removed after the check. No DMS form was submitted and no live SSH connection was attempted. The feature remains `TESTING`.

## DMS-SRV-002 — server list and returned rows

DMS's list uses the server table fields ID, provider, name, main IP, country, expiry, installed flag, SSH history/status, total IPs, allowed-user count, and row actions. The `returned` checkbox changes the data query to soft-deleted rows. The live UI confirms the table headers, 50-row page size, selection toolbar, search field, returned toggle and Add modal. A synthetic no-match search displayed the DMS empty filtered state; AlphaLink displayed the same message with a different total count because the local fixture set was intentionally smaller. The list source shows separate endpoints/modals for IP details and allowed users plus history, console, update, lock/disable, delete and restore actions. Mutating DMS actions were not invoked.

AlphaLink currently returns workspace-scoped active or soft-deleted rows and passes local tests for both queries. It does not yet model the DMS country/history/install/lock/allowed-user/discovered-IP relations. Its row-level actions remain disabled. Those columns and actions are not accepted as equivalent until their exact source business rules, failure cases, and local behavior are established and compared.

Fields without a source-backed local relation now remain `null` in the list JSON and render as `N/A`; they are not represented as false/zero/empty. This avoids claiming a server is uninstalled, unlocked, has no related IPs, or has no allowed users when AlphaLink does not yet know those values. This honesty state is a documented visual difference and does not satisfy DMS row parity.

## DMS-INST-001 — cloud bulk-install selection and eligibility

**Evidence:** E-INST-01 traces the read-only DMS controller, domain action, Blade page and installer command. E-INST-LIVE-01 captures the DMS page through the existing proxy-backed GET-only relay with synthetic server/domain labels, plus its empty state. No installation, server connection, or live log route was invoked.

On page load, DMS lists servers that are active, not installed, named with the authenticated username pattern (`%_` plus uppercase username plus `%`), ordered by descending server ID. Domains must have `free` or `new` status, be active and non-owned, and belong to an active provider. The page defaults to PMTA 4.0; 4.5 and 5.0 are alternatives. Tracking, Proxy, IMAP, SPF, DKIM, DMARC and HTTPS are independent switches that default off.

Each row has a domain selector and an APPLY checkbox. Clicking APPLY prevents the checkbox's default toggle and copies the source row's selected domain to every current row. It does not mark the row for installation. In DMS, INSTALL first removes rows whose domain is empty, then serializes every remaining row. The controller takes each row's `id` and `domain`, validates the PMTA version and all seven booleans, and starts `servers:install_bulk` with the data and options. The browser polls the token-scoped log every two seconds and stops polling after 20 seconds. The source command then performs the remote install; its outcome is not demonstrated by a read-only page capture.

AlphaLink's `/infrastructure/bulk-install` page now applies the source-backed eligibility filters and renders the version/switch controls, candidate rows, domain selectors, APPLY-to-all interaction, removal control, and “This Grid Is Empty” state. Local feature tests cover username-pattern matching, active/uninstalled server status, `free`/`new` domains, active provider, non-owned status, and the actual page labels. The DMS empty state was visually compared in the browser. Existing AlphaLink users have no username mapping by default, and existing domains have no DMS provider/status mapping; unmapped records are excluded rather than guessed eligible.

**Difference and status:** This is a partially implemented planning page, not installation parity. AlphaLink currently has no DMS provider catalogue workflow, server IP topology, subdomain/ISP/VMTA assignment, install payload endpoint, worker, or progress-log route. INSTALL remains disabled. The option controls are present but are not submitted. The DMS page contains no operator fingerprint field; AlphaLink's automatic first-use host-key pin remains an internal transport safeguard for separate read-only preflight behavior.
