# AlphaLink UI behavior contract

This document defines current AlphaLink interface behavior. It is scoped to AlphaLink's own workspace, application data, and permissions.

## Product context

- **Users:** Workspace owners, administrators, campaign operators, and privacy officers.
- **Primary tasks:** Manage audiences and campaigns, review engagement data, configure providers, and operate authorized server controls.
- **Design system:** `resources/css/app.css` owns runtime tokens; `DESIGN.md` documents their use.
- **Language and dates:** English interface; dates use the configured application timezone.
- **Accessibility:** Keep semantic headings and controls, keyboard operation, visible focus, accessible status names, and readable contrast.

## Core workflows

| Area | Current behavior | Verification source |
|---|---|---|
| Sign-in and workspace | Laravel session authentication; users can enter only workspaces where they have active membership. Controllers scope data and actions to that workspace. | Auth and workspace authorization feature tests. |
| Audience lists | Lists are associated with an ISP and country and can hold multiple membership states. Operators can search, import, segment, and review action totals where event data exists. | Audience-list management, import, history, and tracking tests. |
| Audience mixes | Campaign targeting opens the same full mix builder used by the Mix page, including list/email-type selection, profile/device/date/domain criteria, and include/exclude activity filters. A created mix is added to campaign targeting and remains selectable for 24 hours; history lists the owner’s mixes and allows expired criteria to be remixed. | Audience Mix workflow and campaign send-catalog feature tests; browser check for dialog and focus behavior. |
| Campaigns | Campaign content is revisioned. A campaign send selects one ISP and country, with multiple lists or audience segments within that selection. Preparation excludes matches from the selected Offer's saved suppression file and persisted Offer/List exclusions. The separately named Negative Token File is only substituted at the `[negative]` message placeholder; it is not a recipient suppression source. Sending to another ISP or country requires another campaign. | Campaign composer, audience snapshot, and send execution tests. |

Offer/List exclusion runs apply the selected Offer's saved suppression file to the chosen audience and persist reusable matches. Campaign preparation applies those matches automatically for the same Offer and List; the run does not need to be selected in the composer. The Negative Token Files page is a different feature for message placeholder content and must not be labeled as the campaign suppression catalog.
| Tracking and analytics | Open, click, lead, unsubscribe, and bot events are recorded through AlphaLink endpoints and shown only where source data exists. Tracking signals can be affected by scanners and privacy proxies; reports should distinguish raw requests from unique recipient actions. | Campaign and drop tracking tests; analytics and visitor tests. |
| Infrastructure | Server registration, provider settings, installation, domain changes, PMTA controls, and logs are workspace-scoped and retain their separate operational gates. | Infrastructure, provider, and installation tests. |
| Settings and operations | General settings, health, application errors, and queue status are shown through workspace-authorized pages. Sensitive configuration values are not prefilled into forms or returned to clients. | Settings, health, and application error tests. |
| Team communications | Owner/Admin create workspace tasks, messages, or notifications for active admins/operators as a group or one active operator. Tasks and messages appear in the header inbox; notifications appear in the bell. Recipients can read their own records and complete their own tasks. Admin controls live under Workspace Settings and user-specific history appears in Global User Account. App Health remains linked inside the Admin/Owner bell panel. | Workspace membership, global access role, communication recipient snapshots, and scoped controller actions. Check unauthorized roles, cross-workspace IDs, assignment, read state, completion, and archive behavior. |

## Permissions and state

- Navigation visibility is a convenience; direct requests are authorized in controllers and policies.
- Cross-workspace records are not exposed through direct identifiers.
- Destructive or connected operations require their explicit confirmation or readiness gate.
- Empty states must say when no records are available instead of inventing sample data.
- Forms preserve user-authored campaign HTML during editing. Send-time substitutions apply only to declared AlphaLink tracking tokens.

## Command OS dashboard visualizations

- **Deliverability by GEO:** The world silhouette is a geographic reference. Country dots and halo markers are driven only by country-coded workspace event or imported feedback totals. A marker denotes an approximate country-level aggregate, not a recipient location. The side list shows event counts and a relative-engagement bar; neither is a delivery-rate percentage. Delivery/bounce feedback remains a count because the complete sent-recipient denominator is unavailable. Empty date ranges keep the map but show a clear no-country-data state.
- **Marketing Graph:** The AlphaLink hub connects featured workspace modules with radial, module-colored spokes; other authorized modules remain selectable in a compact row beneath the graph. Spokes describe module membership, not links between specific records. Selecting a module exposes its date-filtered count. Hover and keyboard focus bring the active module forward while softening the others. The graph must fit its panel without clipping at supported breakpoints and keep all authorized modules represented.
- Both panels follow the Command OS light/dark theme. At narrow widths, the GEO country summary stacks below the map and the graph recomputes its radial layout to fit the panel.
- **Partner revenue:** Provider-reported sponsor conversions use the same inclusive date range as the dashboard and are grouped by sponsor and provider currency. Different currencies are never combined. Provider totals stay separate from AlphaLink-attributed campaign and Drop lead revenue; conversions without a verified AlphaLink reference do not receive campaign, ISP, mailer, or offer attribution. Workspace operators do not see workspace-wide provider revenue that cannot be scoped to their own records.

## Verification

Use focused PHPUnit suites for the affected controller, service, persistence, and UI behavior. Run PHP syntax checks and `vendor/bin/pint --dirty --format agent` after PHP changes. For browser work, verify the actual AlphaLink page and state when the local environment is available; synthetic fixtures do not establish production data or delivery behavior.

An unavailable dashboard action is rendered as a focusable `aria-disabled` button with a visible reason connected by `aria-describedby`. It intentionally has no destination and cannot navigate or mutate state; static detectors that flag it as an actionless button are reporting an unavailable-state control, not a missing action handler.
