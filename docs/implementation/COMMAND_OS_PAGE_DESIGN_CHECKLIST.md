# Command OS page redesign checklist

**Inventory captured:** 2026-11-08 from the current AlphaLink checkout.
**Goal:** migrate each user-facing AlphaLink screen to the approved Command OS visual system without changing its route, permissions, data semantics, or workflow.

## Inventory basis

- Found **116 page templates** that extend an application layout (shared layouts and partials excluded).
- The route-level source of truth remains [`COMMAND_OS_ROUTE_INVENTORY.csv`](COMMAND_OS_ROUTE_INVENTORY.csv), which records 783 declarations (743 web and 40 API). API endpoints are not UI pages; route declarations may share one screen or represent actions.
- [`ALPHALINK_PAGE_FAMILY_COVERAGE.md`](ALPHALINK_PAGE_FAMILY_COVERAGE.md) maps routes to controllers, views, tests, and known behavior gaps.
- The approved visual references are the Dashboard (`console/analytics/index`) and My Campaigns (`console/campaigns/index`). Their visual styles are references; neither reference alone closes route, permission, responsive, or regression gates.
- `PENDING` means no current page-level Command OS acceptance record is attached here; it does not claim that the screen has never received prior styling.

## Per-screen acceptance gate

For each template, record the canonical route(s) and preserved fields/actions; verify authorization and success/failure/empty states; test light and dark themes, desktop and narrow layouts, keyboard/focus and reduced motion; compare matched browser captures; run focused regression tests; then record `ACCEPTED` only after all applicable checks pass.

## Current slice — Workspace Users / Add User

- Route: `GET /users/create` (`clean.console.users.create`); submit: `POST /users` (`clean.console.users.store`).
- Live baseline: the shared Command OS shell is dark, but the form body is a bright legacy card with very low-contrast labels. The page contains Full Name, Login Email, Username, User Type, User Roles, Workspace Role, Save, Cancel, API validation feedback, generated credential display, and Copy login details.
- Authorization: workspace owners/admins manage members; membership scope and allowed roles are enforced by the existing controller. No account creation or credential mutation is part of visual verification.
- Acceptance is open until the redesigned view passes focused tests and actual production browser checks in both themes and at desktop/narrow viewports.
