# Source-backed business rules in the active server slice

## DMS-SRV-001 — server registration

**Evidence:** E-SRV-01 is the read-only source snapshot at `resources/views/admin/servers/create.blade.php`, `app/Http/Controllers/Admin/ServerController.php:58-111`, and `app/Actions/ServerAction.php:23-65`. E-SRV-LIVE-01 is a fresh browser observation through the authenticated GET-only relay; it confirms the live form and its visible defaults but is not a live registration test.

The DMS form presents a provider dropdown, name (default `server`), an IP textarea, port (default 22), SSH username (default `root`), login type (`Password` or `Ssh Key`), credential, expiry (default approximately 30 days), **TEST CONNECTION**, and **SAVE**. The form's IP handling splits on newline, removes blank strings and exact duplicates; it does not trim each line. The controller requires a numeric provider ID, name string length 2–255, at least one IP, numeric port, username, login type in `password|ssh_key`, credential length at least four, and an expiry date no earlier than today. Exact provider-existence validation, invalid-line feedback and current provider catalogue state are not established here.

`ServerAction::add` processes each supplied IP. A valid IP matching a soft-deleted server is restored and its registration fields refreshed. Remaining new IPs are inserted in one bulk `insertOrIgnore`, so live duplicates are not replaced. There is no transaction covering the whole multi-IP operation: an earlier restore is not rolled back because a later new-row operation fails. Each new server is a separate server record for one IP. DMS Test Connection is a separate request: it validates connection fields and invokes the SSH/SFTP handler for each IP. The DMS form has no fingerprint field or confirmation step; source shows no explicit fingerprint input at the Test Connection or installer call site. Live connection outcomes were not exercised.

AlphaLink implements the same visible form order/defaults, newline split/blank removal/exact deduplication, provider dropdown order seen in the live page, per-IP cardinality, duplicate skip and restore path. It uses a local transaction for a new-record batch and protects credentials with application encryption, workspace-scoped access, idempotency, and an append-only audit record. Test Connection now logs in directly over SSH/SFTP without asking for a fingerprint. Installation preflight automatically pins the SSH host key on first use and rejects a later key change without requesting user input. That automatic pin is an internal transport safeguard, not a DMS business rule. The provider catalogue's authoritative current contents, DMS credential storage rules, exact multi-IP partial-failure response, and real Test Connection result equivalence remain unresolved. Private, reserved and special-use IP ranges that the PHP filter accepted are blocked before local socket creation using the IANA registry ranges in E-ADDR-01; this is an AlphaLink safety boundary.

Browser evidence confirms the DMS and AlphaLink Add forms and their Add modals were compared at the same 863×892 viewport. A local synthetic registration was saved, appeared in the workspace-scoped server list without returning the secret, and was removed after the check. No DMS form was submitted and no live SSH connection was attempted. The feature remains `TESTING`.

## DMS-SRV-002 — server list and returned rows

DMS's list uses the server table fields ID, provider, name, main IP, country, expiry, installed flag, SSH history/status, total IPs, allowed-user count, and row actions. The `returned` checkbox changes the data query to soft-deleted rows. The live UI confirms the table headers, 50-row page size, selection toolbar, search field, returned toggle and Add modal. A synthetic no-match search displayed the DMS empty filtered state; AlphaLink displayed the same message with a different total count because the local fixture set was intentionally smaller.

The DMS controller applies `isAllowed(auth()->id())` to the list for mailer accounts, including when `returned=true`. AlphaLink maps that assignment boundary to workspace `operator` members: operators see only assigned servers; owners/admins see all workspace servers. This is an explicit role-model adaptation because AlphaLink has no DMS account `type` or user active flag. DMS's active-mailer picker maps to current workspace operators; current membership is the target's active-membership signal.

Fields without a source-backed local relation remain `null` and render as `N/A`; AlphaLink does not claim a country or discovered IP count. The STATUS column now shows the newest local SSH snapshot if one exists. It also stores `is_locked` and per-server allowed users. Local tests verify workspace-scoped active and returned queries, operator row filtering, and hidden secrets. Browser comparison of the newly enabled controls is still pending.

## DMS-SRV-003 — allowed users, lock, status, return and restore

**Evidence:** read-only source at `routes/admin.php` (the server routes are under `can:have-role,'manage_servers'`), `ServerController::index`, `bulk_users`, `update_bulk_users`, `users`, `update_users`, `lock`, `status`, `restore`, `destroy`, `history`, `ServerAction::safe_delete`, `Server` model, and `resources/views/admin/servers/index.blade.php`, `users.blade.php`, and `bulk_users.blade.php`. No DMS mutation endpoint was called.

DMS Allowed Users stores integer IDs for active mailer accounts in the server's `allowed_users` JSON. The row button opens a checkbox form preselected from that array; the toolbar action assigns one selected user set to every selected server. Saving an empty array clears the assignment. Mailer access filters the server list to assigned rows, gates status changes and history by assignment, and passes the mailer ID to `safe_delete`. `safe_delete` soft-deletes only unlocked servers, so DMS's **DELETE** action is a reversible **RETURN**. The table hides status and delete controls when locked; the lock endpoint changes `is_locked`. Restore queries only soft-deleted rows and restores them. Its source comment says “if still installed,” but the method does not check `is_installed`.

AlphaLink implements owner/admin-only individual and bulk assignment forms, operator-only selection within the same workspace, assigned-operator list filtering, assigned-operator status changes and returns, and owner/admin lock and restore controls. Returning is a soft delete; locked rows are omitted from the delete query; restore keeps the assigned users. Each change appends an audit event. Tests cover cross-workspace assignment rejection, only-operator assignment, bulk replace/clear, operator visibility and action limits, locked return rejection, status toggling, and restore. This is HTTP/business-logic equivalence for the implemented paths, not complete DMS parity: AlphaLink still lacks automatic health snapshot collection, shell, edit, and discovered-IP behavior; its workspace-role mapping is an adaptation; and browser interaction has not yet been compared for these new controls.

## DMS-SRV-004 — server health snapshots and history

**Evidence:** E-SRV-03 traces `ServerCheckStatus`, the scheduled task, `ServerHistory`, its migration, the list's latest-history relation, and the history Blade table. No DMS job, network check, or history endpoint was run.

DMS schedules `server:check_status` every ten minutes, without overlap and in the background. It considers active, installed servers, unless an explicit server-ID subset is supplied. For each server it checks SSH on the configured SSH port, Apache over port 80, and PMTA on the configured PMTA port concurrently. It stores whether each service is down, with a timestamp. If country is missing, it also performs an IP geolocation lookup. The server list shows the newest snapshot's SSH status; returned rows do not load history. The history page uses server-side DataTables with ID, SSH-down, Apache-down, PMTA-down and timestamp columns, plus refresh and page-length controls. The pruning query deletes entries older than three months; its “1 month” comment is stale.

AlphaLink has workspace-scoped snapshots, an assigned-user-gated history page, and a scheduled collector for active, installed servers. The collector initiates concurrent raw TCP checks for the configured SSH port, HTTP port 80, and configured PMTA port, then persists down flags for the list and history page. It uses no SSH username, key, password, handshake, or fingerprint prompt. PMTA defaults to the DMS settings-form fallback of 1212 and can be configured with `INFRASTRUCTURE_PMTA_PORT`; the timeout defaults to ten seconds. A daily model-prune task removes history older than three months. Country resolution uses the same Pro IP-API endpoint, fields and end-of-day success cache as DMS when `INFRASTRUCTURE_IP_API_KEY` is configured. The source-backed MaxMind city fallback only runs if GeoIP2 and a database file are installed; GeoIP2 is not currently a target dependency, so API-error fallback is incomplete. Focused tests pass with 6 tests/27 assertions; the full suite passes with 34/397; Pint and `schedule:list` pass. Tests fake HTTP and use loopback only; no external server or geolocation request was made. This feature remains `IMPLEMENTING`.

## DMS-INST-001 — cloud bulk-install selection and eligibility

**Evidence:** E-INST-01 and E-INST-02 trace the read-only DMS controller, domain action, Blade page, installer command and OS factory. E-INST-LIVE-01 captures the DMS page through the existing proxy-backed GET-only relay with synthetic server/domain labels, plus its empty state. E-INST-03/04 record local synthetic tests only. No installation, server connection, or live log route was invoked.

On page load, DMS lists servers that are active, not installed, named with the authenticated username pattern (`%_` plus uppercase username plus `%`), ordered by descending server ID. Domains must have `free` or `new` status, be active and non-owned, and belong to an active provider. The page defaults to PMTA 4.0; 4.5 and 5.0 are alternatives. Tracking, Proxy, IMAP, SPF, DKIM, DMARC and HTTPS are independent switches that default off.

Each row has a domain selector and an APPLY checkbox. Clicking APPLY prevents the checkbox's default toggle and copies the source row's selected domain to every current row. It does not mark the row for installation. In DMS, INSTALL first removes rows whose domain is empty, then serializes every remaining row. The controller keeps each row's `id` and `domain`, validates the PMTA version and all seven booleans, and invokes `servers:install_bulk`. The browser polls the token log every two seconds while the request is pending, then clears its polling interval twenty seconds after the request completes.

The submission endpoint requires at least one row, a numeric log key, PMTA 4.0/4.5/5.0, and all seven boolean options. It writes `Installation Started` under the key and runs the child Artisan process synchronously with a 30-minute PHP execution limit and no process timeout. The command forks one installer per row. Per server, it rejects an already-installed server or a domain marked `used`, discovers server IPs, rejects an empty IP set, logs in over SSH/SFTP with the configured username and credential, and checks x86_64 architecture and supported OS release (CentOS Linux 7, CentOS Stream 9, Rocky Linux 9, AlmaLinux 9). It configures the host/services, then runs option-driven tracking/PHP, DNS, IMAP, proxy and HTTPS setup, installs PMTA and VMTAs, configures the firewall, records IP/domain/install config and marks the server installed. A per-server exception is caught and logged, so the outer process/HTTP status can succeed while one or more servers failed. Source shows no fingerprint field/prompt or explicit host-key pin. The OS-specific shell commands, artifacts/license, provider secrets and remote effects still require isolated verification before enabling a local worker.

AlphaLink's `/infrastructure/bulk-install` page applies the source-backed eligibility filters and renders the version/switch controls, candidate rows, domain selectors, APPLY-to-all interaction, confirmed row removal, and “This Grid Is Empty” state. APPLY copies the selected option index to each row, including the blank option, and blocks an owned-domain option. The submission builder drops rows without a selected domain and serializes the DMS form fields; the backend normalizer validates the nonempty row list, numeric key, PMTA version 40/45/50 and seven booleans, then keeps only each row's server and domain IDs. Synthetic tests cover this contract and per-row error logging without a real runner. Separately, AlphaLink saves DMS's `PRETTY_NAME` during read-only host preflight and uses the traced x86_64/OS support matrix to block incompatible hosts in an installation-plan preview. Existing AlphaLink users have no username mapping by default, and existing domains have no DMS provider/status mapping; unmapped records are excluded rather than guessed eligible.

**Difference and status:** This is a partially implemented planning/request-contract slice, not installation parity. The local normalizer and fake-runner coordinator are not exposed by a route, and no production runner is registered. AlphaLink has no DMS provider catalogue workflow, server IP topology, subdomain/ISP/VMTA assignment, persisted run/log lifecycle, or synchronous per-server parallel worker. INSTALL remains disabled. The OS-specific shell steps, supported package/license matrix, provider secrets/writes, rollback and remote health checks have not been reconstructed or locally proven. The DMS page contains no operator fingerprint field; AlphaLink's automatic first-use host-key pin remains an internal safeguard for separate read-only preflight behavior.
