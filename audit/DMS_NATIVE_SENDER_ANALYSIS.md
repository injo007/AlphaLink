## Static implementation evidence

### Phase 3F Ghidra findings — **VERIFIED at the apphost layer**

- The linked entry routine `0x18910` is Ghidra address `0x118910` (`FUN_00118910`, 168 bytes). It performs startup/logging setup, passes `argc` and `argv` to `0x1180b0`, then calls a cleanup/output helper and returns the dispatch result. Its banner identifies the .NET apphost as version `7.0.13`.
- The linked dispatcher `0x180b0` is `0x1180b0` (`FUN_001180b0`, 1,706 bytes, 75 basic blocks). It resolves the executable/application paths and selects .NET host entry points. It forwards the original arguments to `hostfxr_main_startupinfo` or, when the bundle-header field is nonzero, `hostfxr_main_bundle_startupinfo`. Seven call instructions in this routine had no resolved destination in Ghidra's ReferenceManager, so helper-to-resolver edges are not all known. The observed `send.dll` string is the apphost's application-DLL name. The bundle-header field at `0x124010` was nonzero in both files (`c034460000000000` for `send`, `c03c460000000000` for `send1`); interpreted as an offset, each value is 995 bytes before the respective file's end. This is consistent with the observed single-file bundle branch. At the Phase 3F checkpoint, its internal assembly list was not yet known; Phase 3G's verified manifest inventory appears below.
- The linked dynamic-loading routine `0x12b30` is `0x112b30` (`FUN_00112b30`, 1,245 bytes). It constructs a library path, calls `dlopen`, resolves the requested symbol with `dlsym`, checks `dlerror`, uses `dladdr` to identify the resolved image, and closes a failed handle. When the initial `dlopen` fails, it scans `/proc/self/maps` for a matching already-mapped path before trying again. Its observed caller `0x117d80` passes `libhostfxr.so` and `hostfxr_main`. This is .NET runtime bootstrap resolution, not evidence of SMTP or PMTA loading.
- Relevant apphost strings include `libhostfxr.so`, `libcoreclr.so`, `.runtimeconfig.json`, `.deps.json`, `hostfxr_main_startupinfo`, `hostfxr_main_bundle_startupinfo`, and `send.dll`. These identify the runtime-host boundary. They do not reveal the managed sender's parser, mail library, or transport.

### Program entry and argument handoff — **Phase 3 baseline; confirmed by Phase 3F**

- `_start` at `0xc000` loads the program-entry pointer from a relative relocation at `.got` address `0x232c8`; the relocation addend is `0x18910`, the target passed to `__libc_start_main`.
- No symbol named `main` was present at that target. Disassembly at `0x18910` consumes `argc`/`argv`, calls internal code at `0x180b0` with those arguments, retains its return value, and invokes a cleanup/output helper. This establishes a command-line dispatch boundary, not the mode semantics.
- The routine at `0x180b0` contains argument/string/path-oriented control flow and calls internal helpers. Phase 3F shows it is the .NET apphost dispatcher; config parsing and accepted send modes lie beyond this native host routine and remain unknown.
- PHP source already establishes the caller contract: `CampaignAction` constructs a Base64-encoded JSON configuration file and passes a mode such as `send_<mode>` and a config path to the configured ELF (`CampaignAction.php:293-328,448-470`; `BackgroundProcess.php:41-63`). The ELF's argument handoff is consistent with that contract, but does not prove that it parses every supplied field as intended.

### Dynamic module loading — **VERIFIED .NET hostfxr resolution**

- Disassembly shows code at `0x12b30` constructing a path from a global base path and a supplied name, calling `dlopen` with flags `5`, resolving a second name through `dlsym`, checking `dlerror`, and consulting `dladdr`. The direct caller observed at `0x17d9d` passes two fixed `.rodata` references. A failure branch calls a formatted output helper.
- Phase 3F decompilation resolves the caller at `0x117d80` (Ghidra address) and shows it passes `libhostfxr.so` plus `hostfxr_main` to the loader. The loaded module and purpose are therefore identified as .NET runtime bootstrap, not as a mail transport module.
- The ELF's `dlopen`/`dlsym` path is not evidence that SMTP/PMTA handling is in the native apphost. The RUNPATH and absent inspected `netcoredeps` directory do not establish the managed payload's dependencies.

### Imported calls, I/O, concurrency, and failures — **VERIFIED observations**

REA's full disassembly of the native apphost layer contained 25,273 decoded instruction lines and 2,033 call instructions for each artifact, with no `objdump` output truncation. A bounded static classification found:

- **No direct network transport imports/calls observed:** no socket/connect/accept/bind/listen/send/recv, OpenSSL/TLS, cURL, HTTP, or SMTP targets were present in the inspected dynamic-import/call-target set. No `syscall` instruction was observed.
- **Filesystem/path-capable calls present:** `open64`, `fopen64`, `close`, directory enumeration, `access`, `mkdir`, and standard stream/file-buffer operations. Ghidra shows path resolution for the apphost/runtime; no recipient-file read or progress-file write contract was reconstructed from the native host layer.
- **Concurrency evidence is limited to the host layer:** `pthread_mutex_lock` and `pthread_mutex_unlock` are called. No thread-creation/join, fork/exec, or process-spawn import or syscall was observed in the apphost. This does not characterize managed application concurrency.
- **Error/runtime support present:** C++ exception/unwind support, throw helpers, `strerror`, `vfprintf`, `fputs`, `fputc`, and `fflush`. These establish available error/output mechanisms, not the sender's failure classes, retry policy, or recovery behavior.
- **Indirect dispatch remains:** 30 indirect call instructions were observed. Their targets cannot be resolved from this disassembly alone.

### Message and protocol marker scan — **LIMITED NEGATIVE EVIDENCE**

A local static scan of each native apphost `.rodata` section checked only a fixed set of generic markers: common RFC message headers, MIME/version/content-type/transfer-encoding and multipart terms, SMTP EHLO/HELO/MAIL FROM/RCPT TO/STARTTLS/AUTH commands, OpenSSL/cURL markers, `VIRTUAL-MTA`, and selected PHP caller-mode names. No tested marker was found in either `.rodata` section. This is not a full-string inventory; the managed payload was inspected separately in Phase 3G, with its own bounded literal/API coverage described below.

Combined with the absent direct network imports, the evidence does **not** establish native MIME construction, header emission, SMTP connection handling, TLS, SMTP AUTH, PMTA submission, or PHPMailer use. It also does not prove that these functions are absent from another runtime component.
