# AlphaLink master specification

**Authority:** AlphaLink is independently operated. Current user requirements and verified behavior in the AlphaLink application control product decisions. Local historical captures and `LEGACY_` audit files document past behavior for traceability; they do not authorize access to the original service or require AlphaLink to reproduce a behavior unless the user has approved it.

**Systems:** `apps/api` is AlphaLink. `baseheavy.shop` is AlphaLink production. The original service (called DMS in historical evidence) is out of scope: do not connect to it or use its credentials, proxy, database, servers, mail systems, assets, or APIs. Do not import its live data or execute operations against it.

**Evidence order:** Current AlphaLink behavior and tests; explicit user requirements; local archived captures and audit notes; labeled hypotheses. Keep observation separate from inference and retain UNKNOWN where existing evidence does not resolve a question. Do not seek new evidence from the original service.

**Acceptance:** Every feature must pass the gate in `AGENTS.md`. The canonical tracking files are `docs/reference/FEATURE_MATRIX.md`, `docs/reference/EVIDENCE_REGISTER.md`, `docs/implementation/PARITY_REPORT.md`, and `docs/implementation/BLOCKERS.md`. `audit/` contains the earlier detailed reference investigations and remains evidence, with each report's stated limits.

**Current product boundary:** AlphaLink is a separate workspace-oriented application with its own production environment. Archived audit materials describe earlier analysis of another service; they are not a live dependency. Existing feature rows that retain a `DMS-` identifier do so only to preserve links to historical evidence. Installation, sending, provider, and infrastructure workflows keep their recorded AlphaLink-specific safety gates and test statuses; no feature is accepted solely on code presence or a single successful run.

**Implementation loop:** Review current AlphaLink source and tests → use synthetic fixtures for local validation → implement one complete AlphaLink slice → execute deterministic tests → verify only the relevant AlphaLink UI or connected workflow when authorized and safe → record unresolved behavior and update the matrix. Archived captures may be consulted locally; never access the original service for comparison.

**Active phase order:** Dashboard pages → engagement and audience-list data foundation (opens, clicks, leads and unsubscribes) → return to Suppression → Users Management → Tools Encoding → Tools SPF Scanner → Tools Workspace. This is the user's requested sequencing: establish the analytics and list data that suppression will depend on, then resume suppression. Linode/DigitalOcean provider support and PMTA pages/actions have local implementations, but their separate safety gates and connected-operation blockers remain open; this sequence does not waive them. Use AlphaLink source, tests, and authorized AlphaLink runtime evidence for future work; keep unresolved behavior in `TESTING` or `UNKNOWN` rather than accepting it.
